A statically typed language, steeped one compiler stage at a time.

TeapotLang is an experimental, statically typed programming language and compiler written in Python, built as a learning project for exploring lexing, parsing, abstract syntax trees, semantic analysis, and memory-management design.

What this is

A compiler built in the open, in visible stages.

Teapot is not trying to be finished quickly. It's a from-scratch compiler project with a hand-written lexer, recursive-descent parser, dataclass-based AST, and an evolving semantic analysis pass. The project distinguishes between functionality that is implemented and functionality that is still being designed or built.

There is no code generator or executable backend yet. The name is unhurried on purpose: language design, like brewing, doesn't reward rushing the process.

  • LanguageCompiler written in Python, targeting a new statically typed .tp source language
  • StageAlpha — lexer, parser, and AST implemented; semantic analysis in progress; no backend yet
  • Entry pointteapot --input file.tp --trace
  • Memory modes$MEM-GC or $MEM-MANUAL, declared once per source file
  • LicenseGNU GPL v3.0-or-later

The pipeline

Three stages implemented, one in progress, one planned.

The stages below describe the compiler architecture as it currently stands. Each stage consumes the representation produced by the preceding stage.

1

Lexer

Turns raw .tp source into tokens, including keywords, types, literals, operators, comments, and the memory-mode directive.

Implemented
2

Parser

A recursive-descent parser that builds the AST from the token stream, covering structs, enums, errors, operators, functions, default arguments, control flow, casts, arrays, and related expressions.

Implemented
3

Abstract Syntax Tree

A dataclass-based node tree shared by later compiler stages, providing the structured representation used by semantic analysis.

Implemented
4

Semantic Analysis

Builds symbol information across scopes and performs declaration and scope-related checks. Type checking and further semantic rules are still being developed.

In Progress
5

Code Generation

No code-generation backend, runtime, or executable output is implemented yet. This is the next major compiler stage after semantic analysis.

Planned

Syntax

Explicit, period-terminated, and type-first.

Statements use a terminating period. Types carry an explicit mutability prefix: m for mutable and c for constant. Each source file declares its memory-management mode with a single memory directive.

example.tp
$MEM-GC

pub sct Person {
    cstr name.
    csi32 age.
}

pub fc add(csi32 a, csi32 b = 5)!csi32 {
    exit a + b.
}

fc classify(csi32 score)!cstr {
    if (score >= 90) {
        exit "excellent".
    }
    elif (score >= 60) {
        exit "passing".
    }
    else {
        exit "needs work".
    }
}

// entry point
fc main()!void {
    val csi32 total = add(37, 5).
    val cstr result = classify(total).
    val csi32 shown = total >> csi32.
}

Type system

Every type says what it is before it says what it holds.

Integer width and signedness are explicit, while mutability is encoded directly into the type name rather than being supplied as a separate modifier.

Casting between types uses >>, for example total >> cstr. Members are accessed with ::, for example student::grades.

Where it stands

Honest about the gap between parsed and runnable.

  • Works todayLexing, parsing, AST construction, symbol-table construction, duplicate declaration checks, and function parameter scoping
  • Being builtType checking, broader scope resolution, and additional semantic rules
  • Not startedCode generation, an executable backend/runtime, and a standard library
